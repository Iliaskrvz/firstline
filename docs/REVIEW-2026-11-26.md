## Security

### S1. Credits can be bypassed by stopping and restarting a run (high)

**What's wrong:** the credit ledger allows one reservation per lead, ever. When a run is stopped, its leads' credits are
released, and the lead keeps that old, fully released reservation. When the customer starts the run again, the lead is
treated as "already reserved". So nothing is reserved, and the email is written and captured for 0 credits.

The same happens with the new "write anyway" button while a campaign runs: the lead's reservation was released when the
fit check skipped it, so writing it anyway is free.

**Impact:** a customer can get emails for free by stopping and restarting a campaign, repeatedly. Real money: research
and AI costs with no revenue.

**Fix (done):** a lead can take a new reservation once its previous one was fully released.
- Each reservation gets a round number, and at most one is open at a time.
- Capture and release always work on the open round.
- A lead whose last round was charged is never reserved again, so a job that crashed after charging and is retried
  can't charge twice.
- Migration `20261129090000_ledger_reservation_rounds.sql`.
- Tests (`supabase/tests/security-review-pg.test.ts`): stop → restart charges again; "write anyway" charges 1 credit;
  a retried reservation reuses the open one.

**Effort:** half a day.

### S2. The worker crashes when the database drops an idle connection (medium)

**What's wrong:** the worker's database pool has no error listener. When Supabase's pooler closes an idle connection,
Node treats it as an unhandled error and the worker process dies. pm2 restarts it (your deploy table shows 12 restarts),
but the jobs that were running are cut off and retried. Paid AI and Firecrawl calls in them are paid twice.

**Fix (done):**
- an error listener on the pool;
- logging for unexpected promise errors, so they're recorded instead of killing the process silently.

**Effort:** 30 minutes.

### S3. Customer webhooks can be pointed at internal addresses (medium)

**What's wrong:** when a customer adds a webhook URL for the API, we only block a few literal private IP prefixes at the
moment they save it. These still reach internal addresses from our worker:
- a hostname that resolves to an internal address, or to the cloud metadata address 169.254.169.254;
- a redirect;
- IPv6 forms.

The delivery log shows the status code back to the customer, so it can be used to probe what's running inside our server.

**Fix (done):**
- at every delivery, resolve the hostname and refuse private, loopback, link-local and metadata addresses (the check the
  homepage demo already uses);
- don't follow redirects;
- use the same full check when the URL is saved.
- Found while testing: an IPv4 address written as IPv6 in hex (`::ffff:a00:1` = 10.0.0.1) passed the private-address
  check. Fixed in the shared check, which the homepage demo uses too.

**Effort:** 1 hour.

### S4. Failed leads keep their credits reserved (medium, money)

**What's wrong:** when a lead fails after its 3 retries, its reserved credits stay reserved until the customer stops or
ends the campaign. The customer sees "Reserved for running campaigns" stuck at a number they can't use.

**Fix (done):** the worker releases the reservation when the lead fails for good. Running the campaign again
re-reserves it (this needs S1).

**Effort:** 30 minutes.

### S5. No limit on request size (low)

**What's wrong:** Caddy accepts requests of any size. Several routes read the whole body before checking it.

**Impact:** an easy way to use up the server's memory.

**Fix (done):**
- Caddy refuses bodies over 15 MB (CSV uploads go up to 12 MB);
- the sender-report route refuses bodies over 64 KB before reading them.

**Effort:** 15 minutes. It takes effect on your next deploy, which also re-runs the server setup.

### S6. The server says which framework it runs (low)

**What's wrong:** every page sends `X-Powered-By: Next.js`.

**Fix (done):** turn that header off.

**Effort:** 1 minute.

### Noted, not changed now

- **HSTS** has no `includeSubDomains`. That's correct for now, because sslip.io isn't our domain. Add it (and `preload`)
  when FirstLine moves to its own domain.
- **No script Content-Security-Policy.** The pages use inline scripts (Next.js, Turnstile, Plausible), so a script policy
  needs nonces on every page. That's worth doing (about half a day), but it touches every page, so I'd do it as its own
  change after the domain move.

### Checked and fine

- **API keys:** stored as hashes; 60 requests a minute per key.
- **Sender Sheet:** checks its key on every call. The Dodo webhook checks its signature (Standard Webhooks, with a time
  window), and a payment can't add credits twice.
- **Sending-tool webhooks:** compare their URL token in constant time and cap the body size.
- **Microsoft sign-in:** checks that the state belongs to the same user, and uses PKCE. The sign-in callback only
  redirects within the site.
- **Server exposure:** the web app and worker listen only on 127.0.0.1. From outside, ports 3100 and 8787 don't answer;
  only Caddy (80/443) does.
- **Database:** every table has row-level security on. Every server action checks the user's workspace membership.
- **Secrets:** `.env.local` on the server is readable only by the app user, and it is never in git. Integration keys and
  Microsoft tokens are encrypted (AES-256-GCM).
- **Demo and contact form:** the demo refuses internal addresses and has Turnstile and daily limits; the contact form has
  limits per IP and per day.
- **Worker:** every periodic task has its own error handling; one failing task doesn't stop the others.

### C1. The two newest free features aren't on the site (high)

Free email checks (Part A) and the fit check (Part B) mean customers pay only for emails worth sending. The site doesn't
mention either.

This is the strongest argument against the "another tool that burns my money" doubt (loss aversion). It also clearly sets
us apart from competitors, who charge for every lead.

**Proposal:**
- one line under the hero: "Bad addresses and leads that don't fit your customer cost nothing.";
- one card in "Built to be trusted";
- one FAQ answer ("What if a lead isn't a good fit?");
- the same on the Dutch pages.

**Effort:** 1–2 hours.

### C2. "300 emails ≈ €10" next to a €19 minimum (medium)

The price block and the comparison line say "about €10 in credits, once". The smallest pack is €19, so someone who
reads "€10" and then sees €19 at checkout feels misled. Small mismatches like this cost trust at the moment of buying.

**Proposal:** "€19 covers your first 500 emails (about €0.04 each), and 25 are free to start". Keep the per-email
comparison against the $59–167 a month.

**Effort:** 15 minutes.

### C3. Outlook isn't mentioned anywhere (medium)

"Download for Outlook" (.eml drafts) is live. Many small Dutch B2B companies use Microsoft 365, not Gmail. Today the
homepage, the FAQ and the agencies page say Gmail only, so those visitors may think FirstLine isn't for them.

**Proposal:**
- add "Outlook" to the "Send or export to" row;
- one FAQ sentence: "Outlook: download your emails as ready-to-send drafts";
- mention Outlook sending once the Microsoft app registration is done.

**Effort:** 30 minutes.

### C4. No real proof yet (medium, needs you)

There are no customer quotes, logos or results on the site. That's correct: nothing should be invented.

The founder line "Built by a team that runs cold outreach every day" is the only trust signal. If it's true, make it
concrete (your name, photo and one sentence about the outreach you run). People trust a person more than a team name.

When the first users get replies, ask 3 of them for a one-sentence quote and their permission.

**Effort:** your input, then 30 minutes.

### C5. No risk reversal at the moment of buying (medium, needs the lawyer)

The refund offer is built but switched off (`REFUND_OFFER`), waiting for the lawyer. "Unused credits refunded within 14
days" next to the Buy buttons lowers the fear of a wasted €19. Switch it on once the lawyer agrees.

**Effort:** 1 setting.

### C6. The campaign page asks too much at once (medium, activation)

The campaign page's right-hand column now has about ten blocks:
- template;
- writer;
- research depth;
- target customer;
- estimated cost;
- preview;
- run;
- export;
- push;
- sending.

A new user can't see what to do first, and the first preview is where people decide whether to buy.

**Proposal:** show the steps in order ("1 Set up, 2 Free preview, 3 Run, 4 Send"), and fold the later steps away until
the earlier one is done.

**Effort:** half a day.

### C7. The cost estimate ignores free skips (low)

"≤ 240 credits" is the worst case. With the fit check on, add: "Leads that don't fit or have a bad address cost nothing."
That's true, and it reduces hesitation before pressing Run.

**Effort:** 15 minutes.

### C8. The agencies page doesn't sell the per-client target customer (low)

Agencies get the most out of a fit check per client workspace. Add one card: "Each client's ideal customer, checked
before writing."

**Effort:** 15 minutes.

### C9. Signup page: remind people what happens next (low)

Add one line: "Your first 5 researched emails in about 10 minutes." This sets the expectation that brings them back after
confirming their email.

**Effort:** 5 minutes.

### C10. Pricing structure (no change proposed)

Checked against the pricing-strategy guidance:
- **Value metric:** per finished email, which matches the value and is easy to understand.
- **Middle tier:** Growth is marked "Recommended", which is the right decoy setup. Prices end in round numbers (€19 /
  €69 / €299), which fits.
- **Anchor:** the competitor comparison is dated and sourced.
- **Future:** once you have real usage, a 50,000 pack (already prepared, switched off) is the next step. That's a
  decision for after real costs are known, as agreed.
