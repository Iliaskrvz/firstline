## Phase 7: Push to sending tools (shared layer + Instantly)

Build a `SendingTool` adapter interface in src/integrations/ (testConnection, listCampaigns, ensureVariables, pushLeads, handleWebhook, pollStatus) with a fake adapter for tests. Instantly is the first real adapter.

The flow in the app (Send step → "Push to Instantly"):
1. On the Integrations page, the user pastes an API key, tests the connection, and it's saved encrypted. If the key's plan can't use the API or webhooks, say so clearly.
2. The user picks a campaign from a dropdown.
3. Variable mapping: map FirstLine's output fields (subject, each AI slot, the full personalised email) to variable names in the tool. Use sensible defaults that the user can edit.
4. Dry run: push the first 5 leads and show added/skipped, with reasons.
5. Push the rest in batches as a pg-boss job, with progress, retries with backoff, rate-limit handling, and resume after a crash. Skip duplicates and suppressed contacts. Show a results table and a "retry failed" button.
6. Webhooks: give each integration one URL with a secret. Store reply, bounce and unsubscribe as status flags only (no reply bodies). Add bounces and unsubscribes to suppression, and process each event exactly once. If the customer's plan has no webhooks, poll lead status instead.

Instantly notes (check these against the v2 docs): use an API **v2** key. Create the custom variables on the campaign **before** adding leads (`POST /api/v2/campaigns/{id}/variables`), or they won't show up. Then add leads with `POST /api/v2/leads/add` in batches of up to 1,000, with `custom_variables`.

Pushing is free, because the credits were already paid for the personalisation.

**Groundwork for the V2 reply-rate loop:** for every email that leaves FirstLine (Gmail Sender Sheet, push or CSV), store an outcome row with: campaign, tool, skill version, writer tier, slot types used, fact tiers used, and then the outcome (sent / replied / bounced / unsubscribed). Outcome rows hold **no personal data** (no email, name or company), so they can be kept after the 30-day lead deletion. Feed the existing Quality Lab reply-rate view from them.

**Done when:** the dry run, the full push and the webhook events work against the fake Instantly in tests, and against my real Instantly account in a manual test we do together.
**From me:** an Instantly account with API access (I add the key in the app myself) and a test campaign.

## Phase 9: Public API + n8n node + Make app

This is for AI automation builders. The API uses the same credits and ledger as the app, and API usage shows in the ledger as source "api".

- API keys per workspace, created by an owner or admin. Show each key once, store it hashed with a prefix like `fl_live_`, and support revoking it and showing its last-used date.
- v1 endpoints: personalise one lead (lead fields plus either inline copy or a saved campaign's copy, with options for depth and writer tier), a batch of up to N leads, get job, and get credit balance. Make them async by default, with an optional `wait` of up to about 60 seconds, because n8n users want the result in the same step.
- Outbound webhooks (job done, batch done), HMAC-signed with a timestamp, with retries.
- An `Idempotency-Key` header, rate limits per key, and consistent JSON errors. Credits are reserved when a job is accepted, charged on success and released on fallback.
- An OpenAPI 3.1 file plus a docs page in the app with a curl quickstart.
- **n8n:** a package named `n8n-nodes-firstline`, built with the `n8n-node` CLI. Operations: Personalise lead, Get job, Get credits. It uses an API-key credential and English only, and it must pass `npx @n8n/scan-community-package`. n8n now requires community nodes to be published to npm from a GitHub Action with provenance, so set up that workflow. Read docs.n8n.io → "Submit community nodes" before you start.
- **Make:** a custom app with the same three modules. Check Make's current rules for private sharing and public listing.

**Done when:** the API works end to end with the fake provider, the n8n node works in a local n8n (Docker) against my local app, and the Make app's modules are defined and documented.

## Phase 11: Deep and Local add-ons

**Deep (+1 credit per lead):** search for the contact's name + company on the public web, and check it's the same person before using anything.
- Run the match check in code first (company name or domain, title, location), then the AI judge. Below a confident match: use no person facts, charge nothing, and label the lead "no confident match".
- Use only professional, public facts: talks, podcasts, articles, interviews, company announcements. No LinkedIn scraping (spec rule), and nothing about family, health, politics, religion or where they live.
- Person facts get their own tier and source like other facts, they're deleted with the lead data (30-day rule), and the style rules keep openers from sounding creepy.

**Local (+2 credits per lead):** Google rating, review count and review themes for local businesses.
- Before building, read Google's Places API policies and the **EEA** Maps Platform service terms (my billing address is in the EU). Tell me whether using review content to write an email is allowed and what attribution it needs. **Stop if it isn't allowed.**
- Places content may not go into the 30-day domain cache. Only place_id may be cached, and the rest is fetched fresh on every run.
- If you can, use one call with a field mask that finds the place and returns rating and reviews together, to keep cost down.
- No match on Google means no charge.

**Cost check for both add-ons:** at current pack prices, one credit is about €0.030–0.038 before payment fees. With the ×3 rule, Deep can cost at most about €0.010 per lead and Local at most about €0.020–0.025. Measure real cost on 20 real leads for each add-on. If either is over budget, show me options before shipping.

**From me:** a Google Cloud project with billing and a Places API key restricted to the Places API (I add it with `read -rs`), plus real local-business leads for testing.

Also draft updates to the sub-processor list and privacy text for Deep and Local, for the lawyer to review.

## V2: design only, don't build yet

Write docs/V2-DESIGN.md. For each item below, cover prerequisites, real costs, open decisions and a phase plan. Keep the V1.5 interfaces (the sender adapter and the Phase 7 outcome rows) ready for these.

1. **"Connect Google" one-click OAuth.** Sending only needs `gmail.send`, which is a *sensitive* scope: it needs Google's app verification but no security audit. Reading mail to detect replies (`gmail.readonly`, `gmail.modify`, `gmail.metadata`) uses *restricted* scopes, which need a CASA security assessment that has to be redone every year. Lay out both options with their costs: send-only OAuth with reply detection staying in the Sender Sheet, or full OAuth plus CASA. Verification also needs the final brand domain, homepage and privacy policy, which depends on my brand decision.

3. **Agency layer:** an agency workspace with client sub-workspaces and credits allocated from the agency's pool. White-label covers logo, colours, custom domain, hidden FirstLine branding and branded emails.
4. **Reply-rate feedback loop:** import stats (webhooks, Sender Sheet flags, a CSV stats import) and link replies to opener features. Set minimum sample sizes before drawing any conclusion. Use replies only, because opens are unreliable. Get positive vs negative from each tool's own reply labels, without reading reply bodies. Show it in the Quality Lab first, and only later feed winning patterns back into the skill.
